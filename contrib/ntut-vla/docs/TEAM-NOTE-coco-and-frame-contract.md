# 1. COCO is the wrong tool, and here is the measurement

The meeting recorded an action item to *"integrate COCO so the drone can detect
various object classes and different colours"*. I want to push back on it, with
numbers rather than an opinion, because acting on it would cost labelling effort
and make the system worse at the thing it is currently good at.

## The premise is out of date

The item assumes the system is *"limited to a single pre-defined object"*. It is
not. `--object` is a plain string argument, and OWL-ViT is **open-vocabulary** —
it has no fixed class list at all. Measured on a real flight frame, one phrase
per forward pass, exactly as the live system runs it:

| query | score | box centre | box size |
|---|---|---|---|
| "a tree" | 0.431 | (145, 55) | 37×50 |
| "a building" | 0.314 | (95, 42) | 160×84 |
| "a road" | 0.105 | (199, 140) | 398×168 |
| "a traffic light" | 0.078 | (201, 161) | 11×9 |
| "a lamp post" | 0.060 | (240, 92) | 17×28 |

Different phrases, different boxes, each landing somewhere sensible. No training,
no dataset. The class vocabulary is already open today.

## COCO cannot fix what is actually broken

There are two separate problems and COCO addresses neither.

**Grounding in the action model.** AerialVLA ignores its object slot: correct and
wrong colour words produce indistinguishable actions over 108 controlled forward
passes, and flown against a real car it returned 12 identical token triples out
of 12. To fix that you need **(image, instruction, action)** triples where the
action depends on the instruction. **COCO contains no actions.** It is (image,
box, class). It cannot teach an action model grounding even in principle, no
matter how much of it you use.

**Colour.** This is the real limit and it is nine words —
`red, orange, yellow, green, blue, purple, white, black, grey` — in a hue table
in `demo/follow_vlm.py`. Adding a colour is **one line**. It needs no dataset.

## And it would cost something

Fine-tuning OWL-ViT on COCO's 80 fixed classes would erode the zero-shot
generalisation demonstrated in the table above. That generalisation is the asset;
trading it for a closed class list is a downgrade.

## What I suggest instead

1. Extend the hue table when a new colour is needed — one line each.
2. Support several text queries in one forward pass (OWL-ViT already accepts a
   list; the current code sends one).
3. Build the command interface for switching target mid-flight.

None of the three needs a dataset. If the team still wants a dataset campaign
after reading this, the honest target is the *action* model, and the data would
have to be generated by us — spawn several vehicles, vary the instruction, and
make the ground-truth action depend on which one was named.

`docs/RESULT-traffic-and-gapfence-aug2026.md`.

# 2. The frame contract does not match, and it blocks the flight controller

This one needs a decision from Prof. Lai rather than a preference from me, and it
should be settled **before** anyone connects a real flight controller. A wrong
frame in the simulator produces an odd-looking plot. A wrong frame on hardware
flies the aircraft in the wrong direction.

## The mismatch

| | upstream `vlaguard_common.Action4D` | ours `guardrail/models.py:31` |
|---|---|---|
| frame | **body** — vx forward, vy right | **world** — vx +North, vy +East |
| vz | up-positive | up-positive ✅ |
| yaw_rate | rad/s | docstring says deg/s, runtime is rad/s |
| where NED conversion happens | one place, the MAVLink adapter | at the sim adapter |

The upstream design states a hard invariant: *projection operators never see
NED*. Ours breaks it deliberately, and the reason is not laziness.

## Why ours went world-frame

**A geofence projection needs world coordinates to know which way the fence is.**
The Shield's repair operators push the aircraft away from polygon boundaries
defined in world coordinates; expressing that in a body frame means rotating the
constraint geometry on every tick, at every repair iteration, inside a fixed-point
loop. We have a working, tested geofence repair — NFZ time 0.0 s on every flight
ever recorded — and it is world-frame because that is where the constraints live.

I am not claiming upstream is wrong. I am claiming the two cannot both be right,
and that the decision has consequences neither side should make unilaterally.

## Options, as I see them

1. **Adapter converts at our boundary.** We keep world-frame internally and add
   `world_to_body` before publishing `/shield/setpoint`. Smallest change, keeps
   both codebases as they are, costs one rotation per tick.
2. **We move to body-frame.** Honours the upstream invariant, but the geofence
   and clearance operators have to rotate the constraint geometry per tick, and
   every existing flight result would need re-validation.
3. **Upstream relaxes the invariant** for geometric constraints specifically.

My recommendation is option 1, but the call is Prof. Lai's.

## Carry this into the same conversation

`Action4D.yaw_rate` is documented **deg/s** and every producer feeds **rad/s**.
The consequence is that `yaw_rate_max_dps: 45.0` has **never fired in any run in
this repository** — AerialVLA's widest output is 1.1 rad/s, which is 63 °/s and
should be clamped, but as a bare number 1.1 < 45.

It is not a typo fix. Making the cap live would be the first time the Shield edits
`yaw_rate`, and the clean separation the entire follow result rests on — heading
belongs to the pilot, track belongs to the guardrail, verified at 0 yaw edits over
419 violation ticks — would no longer hold. The defect is asserted by
`test_yaw_cap_is_unreachable_at_flight_scale_KNOWN_DEFECT`, which turns red the
day someone changes it.
